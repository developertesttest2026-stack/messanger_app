## 📝 ТЕКУЩАЯ АРХИТЕКТУРА

### Текущие модели:
- **User** — пользователь (telegram_id, username, full_name)
- **ChatRoom** — комната чата (name, description, created_by)
- **RoomMember** — членство в комнате (room_id, user_id)
- **Message** — сообщение (room_id, user_id, text, created_at)
- **LoginSession** — сессия аутентификации

### Текущие API endpoints:
- `POST /auth/create-session` — создание сессии
- `POST /auth/resolve-session` — разрешение сессии
- `POST /auth/verify-code` — подтверждение кода
- `GET /me` — получить текущего пользователя
- `POST /rooms` — создать комнату
- `GET /rooms` — список комнат
- `GET /rooms/{id}` — получить комнату
- `POST /rooms/{id}/messages` — отправить сообщение
- `GET /rooms/{id}/messages` — получить сообщения

## ⚠️ ВАЖНЫЕ ПРИНЦИПЫ

### Безопасность:
- ❌ **НИКОГДА** не конкатенируйте переменные в SQL запросы
- ✅ **ВСЕГДА** используйте параметризованные запросы ORM
- ✅ **ВСЕГДА** проверяйте права доступа на бэкенде
- ✅ Не доверяйте ID из фронтенда — получайте текущего пользователя из токена

### Качество кода:
- Используйте типизацию (Python type hints)
- Добавляйте docstrings к функциям
- Возвращайте правильные HTTP коды:
  - 200 OK — успех
  - 201 Created — создание ресурса
  - 400 Bad Request — ошибка клиента
  - 403 Forbidden — нет прав
  - 404 Not Found — ресурс не найден
  - 500 Internal Server Error — ошибка сервера

### Производительность:
- Пагинируйте большие выборки (не грузите все сразу)
- Используйте debounce для частых запросов с фронтенда
- Индексируйте часто используемые поля БД
- Кешируйте данные когда возможно
